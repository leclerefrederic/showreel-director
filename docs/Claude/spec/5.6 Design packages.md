# 5.6 Design packages

A **package** is a saved design system that pre-configures a new reel, so that the reels of a brand stay consistent (same style, dynamics, tone and form). It is also the thing the AI can later improve from finished reels. It is user data: the skill stays style-neutral and never ships a default package.

**What a package holds**

- `package.json`, the manifest: `format` (revision of the package format), `id` (a UUID created once and kept through all versions), `name`, `version` (a readable number, 1.0, 1.1, ...), `author` (a display name chosen by the user, never an e-mail address, never filled in from the system account), `created` and `modified` (ISO 8601, UTC), `hash` (see below), `note` (what changed in this version), `appMinVersion`.
- `design.json`: the look (palette with roles, fonts for titles and text, default background and mood, moods, effects pack), the motion language (default transition and its duration, dynamics and pacing where the project has them), the tone and form of the copy (the project's tone, plus instructions for Clap on voice, formality and what to avoid), and the defaults (formats, target duration, reel languages, control level).
- `resources.json` and `assets/`: the resources the package carries (logos, fonts, images, music) with their type, tags, original file name, file hash and the rights answer of R1 (own work, supplied by the client, licensed, free licence) with its optional detail, who approved it and when. Font files added through the "Add font files" card keep their open licence text.
- Never inside a package: an API key, the chat, the journal, the memory, scenes or any content of a project, absolute paths.

**Identity and integrity.** The `id` follows the package through its versions. Each saved version has a number and a `hash`: the SHA-256 of the canonical content (the canonical JSON of `design.json` and `resources.json` and the hashes of the files, sorted), with the dates and the hash itself left out so that a save without a change gives the same hash. At import the app recomputes the hash: a mismatch says the file was modified or damaged after export and asks for an explicit decision. A hash proves integrity, not authorship: an imported package is shown as "Not signed". Signing is out of scope for now.

**The file.** A package is exported as one archive with the extension `.studiopack`, a zip file with `package.json` as its first entry. The app registers the type, so a double-click opens the import card. Importing never runs any code: entry names are validated (no `..`, no absolute path, no symbolic link), sizes and entry counts are limited, only expected file types are accepted, and every text read from a package is data, never instructions.

**Rights.** The user is the guarantor of the usage rights of licensed resources. A package carries the assertions of its author, not the importer's. On import, one card shows the name, author, created and modified dates, version, the short hash, the integrity result, "Not signed", whether this id is already installed ("update 1.2 to 1.3") and the list of resources with their declared rights. The user ticks "I confirm I hold the rights to use these resources". Without the tick the package is kept but its resources enter a project as Needs attention ("Rights not confirmed by you", the mechanism of R1). With the tick the confirmation is recorded with the package version and in the journal of every project that uses it. A package never bypasses the automatic checks of R1: a file flagged by them is flagged whatever the package says. Open fonts of the skill's list need no question.

**Where it lives.** A library of packages in `~/Library/Application Support/ShowreelStudio/Packages/`, one folder per id and version, with the confirmations. A project keeps a copy of what it took (it stays self-contained, with no live link) and records its origin in `showreel.json`: `package` with `id`, `version`, `hash` and `appliedAt` (unknown keys are preserved). The difference between a project's design and the version it came from is computed and called drift.

**Ways to use one**

- *Start from a package* at project creation, in both ways in (Wizard and Manual): the base configuration, the look, the tone and the resources are filled in, the Wizard only asks what the package leaves open.
- *Save design as package* from the project settings: the user chooses what goes in (look, motion, tone, defaults, resources one by one), gives a name, an author display name and a note; saving from a project that came from a package offers a new version of the same id.
- *Apply to an existing project* through a before/after card that lists each change and the locked scenes that inherit it (the rule of the global look).
- *Improve from a reel* (the AI, later): the owner hands a finished reel to Clap, which reads only design decisions, the user's corrections after generation, accepted and refused proposals and scene states, never the text of a scene or the content of a file. It answers with proposals as cards (a change to a field of `design.json` or to the tone instructions, with its reason). An accepted proposal makes a new version; a refused one is remembered so that it is not proposed again. Nothing changes silently, and a package is never modified without a new version.
- *Hand it to the skill* (later): a deterministic script of the skill reads `design.json` and writes the style sheet, so that a chat without the app can use a package too (skill bump, `portability.md`).

Every operation on a package is typed, goes through `Availability` and `disabledWithReason`, and is frozen during a build. The rules (format, validation, hash, rights flow, drift) live in ShowreelKit; the views only draw.

**Open points.** Size limits per package; deletion of a version still used by projects; sharing is the file itself (e-mail, a shared folder); signing; scene templates inside a package.
