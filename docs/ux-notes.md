# Showreel Studio: UX notes per block

The owner's remarks while testing, one section per block, newest first. Nothing here is built until the owner turns a note into a brief. Views hold no business logic: they call typed operations, so a rework touches the screen only.

Order of the per-block rework: Project and wizard, Resources, Look, Storyboard and scene, Build and deliver.

## Guiding principle

Action/reaction. The interface is alive: every action gets a visible reaction, and whenever something becomes unavailable (an element no longer editable, a feature not reachable), the interface says so, says why, and says how to get it back. Never a silent disabled control.

- When Clap proposes changes, some elements are no longer editable and some features are unreachable. That is normal, but nothing says so visually.
- While Clap builds the film, nothing may be edited, because any change would affect the film under construction. Closing the window must warn that the work in progress will be lost, and what that means.

## Action/reaction: remaining

Built in Q5 and Q6: the state and reason model (`Availability`, `ProjectActivity`, `Marks`), the freeze during a build, the proposals banner, the temporary marks on every surface (the list, the tree, the reel, the inspector and the resources: a veil around the row and a small button at its end, the same tooltip and the same way to the proposal's card), the persistent badges in one order (review state, then build state), the activity chip, the build panel, the closing alert, the status line with Undo, and the standard disabled control (`disabledWithReason`) on the storyboard review, Save scene, the reel's Apply and Revert, the content item's Apply, Build and Test it again, Reset layout, Validate storyboard, the palette editors, the moods picker, the memory form, the editor's Save, the set-up form and screen, the new project and Update and Restore sheets, the preview pane, the wizard's Back and Next. Undo and Redo of the Edit menu, and the move items of a content item's menu, say why in their own title (a menu item has no tooltip).

Left, and why:
- The state choices of a scene's badge menu (`SceneStateViews.swift`) keep the reason in the item's title; the lock switch and the Go button explain themselves with the text beside them. They do not use the standard control: a menu item and a text-led control do not take one.
- The Library's own buttons other than Create (Open, Remove, Locate, Trash) are never disabled today: nothing to do.
- The music toggle of the player (`PlayerViews.swift`) has a tooltip only ("This build has no music"): a toolbar toggle in a custom bar; it needs a small component of its own.
- Clap's own composer (the send button turning into Stop) has no reason line: its rule (busy, no key) is shown by the connect box and the chip.
- An outdated project stays editable: the banner offers Update project, nothing blocks it. Blocking it would be a new rule (decided by the owner).
- The mark of "Clap is applying changes to S02" is shown on scenes and items only, not on the transition markers, the music lane or the settings rows: a transition and the music are not elements with a row of their own yet.

## Application (launch, library, settings)

- Very important (owner): the project must keep the AI's memory so that what was decided, validated or modified is never lost, even if the user changes the model or relaunches the project: a history of the work sessions. Scheduled as phase M (journal, curated memory, session history).

- The AI assistant is named Clap (the word Copilot is too tied to another product). User-facing only: the right panel tabs are Inspector and Ask Clap (with a clapperboard icon, a badge when a proposal is waiting), the panel header reads "Clap, AI assistant", and the interface says plainly that it is an AI. Code names, tool names and file names keep "copilot" where they exist. If asked what it is, Clap answers honestly that it is an AI assistant built on Claude.

- Library window: the project rows need a hover effect at minimum. Opening a project by double-click is not intuitive: one click opens it (with a clear affordance such as a chevron or an Open button on hover). The grey "start" badge looks clickable and does nothing: show the project's progress as plain status text with a clear meaning (for example Setup, Storyboard, Built), not as a button-like pill.
- Library window: remove the Settings button at the bottom. Application settings live only in the app menu (Showreel Studio, Settings, Cmd+,).

- The scene look bug seen earlier came from leftovers of an old project (data written by an older version of the app). Needed: an explicit way to bring an outdated project up to date, and a way to delete a project. Proposal: `showreel.json` gets a format revision number; the Library marks an outdated project and offers "Update project", which lists what will change, keeps a backup first (`.studio/backups/`), migrates and rebuilds the derived caches, with a way back by restoring the backup. Deleting: "Remove from Library" (files kept) and "Move to Trash..." (confirmation naming the folder and its size, never a permanent deletion); a project whose folder is missing shows as missing with "Locate..." and "Remove".

- Look editor chooser: the dropdown listing Looks, Palette, Fonts, Background, Moods, Effects pack is not intuitive. Proposal: the Look tab of the project settings is a list of six rows (icon, name, the current choice as a swatch or sample); clicking a row opens that editor (drill-in with a back button, like macOS System Settings), with the current choice pinned at the top and the library below.
- A new project must not start without its base configuration, even in Expert mode, because everything else depends on it. Proposal: a required setup at creation, the same data in both modes (the wizard in Beginner, one compact form in Expert), covering the languages (conversation and reel), the formats, the target duration and a look (palette, fonts, default background); the workspace opens only when these are set. Audience, message and tone stay optional.
- Checks: they should live in the left panel as a Checks tab (with a badge counting what is red or orange), grouped by area (Project, Resources, Scenes, Storyboard, Music, Build). Clicking a check opens the element to configure: the project setting, the resource, the scene or the transition concerned.

- The Look tab (palette, fonts, backgrounds, effects, transitions, looks) does not belong in the left library: the look is a project parameter, not an asset like a scene or a resource. The library keeps assets only (Resources, Scenes). Proposal pending validation: the global look (looks board, palette, fonts, default background, mood and effects pack) moves to the project settings in the top bar; the catalogues of effects, transitions and backgrounds become pickers inside the scene inspector (Effects tab, per-scene Look), the transition inspector, plus an optional floating catalogue palette that stays a drag source.

- Project settings belong in the top bar of the project window (one button opening the project's parameters: audience, message, tone, languages, formats, duration, constraints, control level). App settings (API key, gateway, model, environment, skill version) do not belong in the toolbar: they stay in the application menu (Showreel Studio, Settings, Cmd+,), because they are about the app and not about a project.

- Overall feel: too much like a form-based Windows application of the 2000s. More drag and drop everywhere (reorder elements, rearrange, drop resources onto scenes), more fluid, visual and dynamic. Up and Down buttons should go. Scheduled as W5 (direct manipulation) and P (feel).

- Bug seen on screen after the resizable panels: the storyboard strip cannot be resized vertically (the library and inspector widths work).

- Panels (library, inspector, storyboard strip) must resize freely with no imposed maximum, only a sensible minimum; sizes remembered per project. Requested by the owner and added to the W3a pass as a separate item.

- The Library window opens at launch by default (built in phase T).
- History belongs to Clap: memory, sessions and journal are reached from the Clap tab, not from project settings. Le titre de l'onglet est "Ask Clap" avec une icône.
- Selector labels are in English (Conversation, Memory, Sessions, Journal).
- A global look change warns on its card about locked scenes that inherit it; the owner decides.

## Library, Scenes tab

- **Built in T2 (2026-11-09).** The Transitions tab (between Scenes and Checks): one row per pair of consecutive scenes ("S01 to S02: Push, 0.6 s", "Cut"), with the marks "approximate render at assembly" and "instruction pending"; a click selects the marker on the reel and opens its inspector; under the list the catalogue, a drag source for the markers, the six preview-only ones marked and refused at the drop with their reason. Rows that drag (resources, the catalogue, the look's catalogues) are not buttons any more (a button takes the press and no drag starts).

- The tick boxes in the scene list are ugly: use an eye icon, open when the scene is visible in the film and crossed or closed when it is not (the reel already uses an eye). A hidden scene is dimmed; the eye has a tooltip and an accessibility label ("In the film" or "Hidden").
- Seen on the same screenshot: a duration of "0.868 s" after a drag; displayed durations should be rounded to a readable precision (0.1 s, or 0.01 s when zoomed in), and the empty blue circle before the scene ID (review state) has no visible meaning: give each state an icon and a tooltip (to review, approved, to modify).

- Add Transitions to the left column. Proposal: a third tab next to Resources and Scenes (then Checks): the film's transitions as a list, one row per pair of scenes (S01 to S02: Push, 0.6 s), clicking a row selects the transition marker and opens its inspector (type, duration, parameters, instruction for Clap, a preview between the two scene thumbnails); below the list, the catalogue of transitions (with the six preview-only ones marked) as a drag source for the markers of the reel.

- Bug found testing W5: a resource cannot be dragged from the library onto a scene, because Resources and Scenes are separate tabs of the same panel, so the source and the target are never visible together. Fix: the reel frames (always visible) and the selected scene's inspector accept drops. Settled in UI1: Resources and Storyboard are stacked sections of the left panel and are always visible together, so no tab has to switch while a drag hovers (the spring-loaded tab idea is dropped).

- A scene can be renamed (a name chosen by the user, shown next to its ID). The ID (S01, S02) stays stable and is never renamed or reused; the name is only a label, used in the library, the tree, the reel and the copilot's messages.

- Each scene must expand into a tree of what composes it: Raw (images, sound, etc.), Texts, Effects, Background (inherited from the project), Look (inherited from the project). The goal is to see at a glance what a scene is made of (scheduled as phase W1b).

- **Proposed restructure (owner, 2026-11-09, to schedule after the Build audit BA1; revisit before building).** Three regions with one job each: left = what is in the film, middle = what you see, right = what you set.
  - **Vocabulary.** Storyboard = the plan of the montage (scenes in order, their durations and transitions). Film = the assembled, playable result ("Film not assembled"). The strip at the bottom and the left list are two views of the same storyboard, with the selection in step.
  - **Phase 1.** Merge the Scenes and Transitions tabs into one "Storyboard" tab (then Resources, Storyboard, Checks): a flat list of scenes in order with a thin line between two scenes for the transition ("to Cross dissolve, 0.8 s", never unfolded). Under it a section "Not in the storyboard" for archived and switched-off scenes. The transition catalogue stays in the floating Catalogue. Reordering by handle must move a transition with its scene.
  - **Left list rows carry state icons only, no detail layer and no tree:** handle, ID and name, then a small fixed set of icons (review state, locked, build state, layout warnings), each with a tooltip that gives the reason. At most about four, in a fixed order, so a row never turns into noise.
  - **Phase 2.** Move the scene tree (Composition, Effects, Look) to the top of the Inspector tab as an overview of the selected element (the Composition tab already covers part of it); the middle shows the selected element; the right keeps details and settings (Ask Clap stays its own tab). Check the density of the right panel first.
  - **Preview caveat.** Drafts and thumbnails are stand-ins of the look today (no 3D, no real scene). A faithful preview of one scene needs a one-scene assembled page (scenes are separate files since BG1c): to measure speed and fidelity before promising it.
  - **Drop targets.** The flat list and the inspector must both accept a resource dropped on a scene (the inspector has no scene target yet).
  - **No Resources tab (owner, same day).** Split the left panel vertically instead of using tabs: the storyboard on top (about two thirds), the resource browser below (about one third), so a resource and the scene it goes to are always visible together (this removes the cause of the "resource cannot be dragged onto a scene" bug, which came from the two living in different tabs). The divider is draggable and the resource section can be collapsed or opened to full height for the heavy work (rights, details, tags). To settle before building: where the Checks tab goes (a badge with the count of red and orange items in the top bar that opens the list, or a thin status row at the bottom of the left panel), and how much vertical room is left next to the storyboard strip on a laptop screen.
  - **Scene row icons, decided by the owner (2026-11-09, after seeing UI1).** Three fixed columns, always present: (1) Status, read-only, one icon; (2) Visible (eye open or crossed, a click toggles); (3) Locked (lock closed or open and faint, a click toggles). Status priority, worst first: Needs attention (red exclamation: the scene's code test failed), Not written (dashed grey circle: no file, empty frame), Out of date (blue circular arrows: the scene changed since it was written), Layout warning (yellow triangle), To review (orange hammer: not reviewed yet, or a modification was requested, the note shown in the tooltip), Ready (green check; called Ready, not Approved, in the interface). "To modify" is not a status: asking for a modification puts the scene back to To review. The tooltip lists every state of the scene with its reason; one pure function in ShowreelKit decides the icon and both the left list and the strip's frames call it.
  - **Lock, owner's rule.** A locked scene is frozen in time and space, visible or hidden: no change to its content, look, duration, visibility or place, and never rewritten by a Build. Recommended and awaiting the owner's yes: a change elsewhere that would move a locked scene (inserting before it, lengthening an earlier scene) is refused with the reason and the way out (unlock it, or change a scene after it), and locking takes a copy of the scene's effective look so that global look changes no longer touch it (the "apply anyway" card disappears for locked scenes). Unlock stays possible, with Undo.
  - **Review mechanism to rethink (owner, same day): OK, MODIFY and DITCH "make no sense ergonomically".** With the three icons they duplicate them: OK is Ready, MODIFY is To review with a note, DITCH is "not in the storyboard". **Decided by the owner (same day): three switches in the inspector, Visible, Locked and Ready, and a "Delete scene" button at the bottom** (UI2). Recommended defaults awaiting the owner's yes: Ready off means To review, and a modification request is just the scene's existing instruction field; only a Ready scene can be locked (the lock says "Make the scene Ready first"); the Go gate becomes "every visible scene is Ready" (a locked scene is Ready, a hidden one is ignored); Delete scene really deletes, with a confirmation, Undo and a journal line, and is refused on a locked scene with its reason; "Not in the storyboard" then holds only hidden scenes; Clap never sets Ready for the user, it can only propose it. Clap's tools and the journal must follow; keep the stored state names as they are if renaming them would need a migration.

## Inspector, scene

- Remove the "Project" button at the top right of the scene inspector header: the project settings are already always reachable from the top bar.

- Bug seen in use: turning off a scene's look override (switch off) does not show the project's values again, neither in the Look tab nor in the scene tree on the left: the flag says Inherited but the customised values are still displayed.

- Scene Content and Resources tabs merge: an attached resource and a text are both elements of the scene. Proposed name: Composition (a scene is a composition of elements); the items are called elements. Scene inspector tabs become Settings, Composition, Effects, Look.
- The scene tree and the inspector use the same structure: Composition (the elements in priority order, texts, images and sounds mixed, since the order is the priority), Effects (scene-wide), Look (Background, Palette, Fonts, each shown as inherited or overridden). Settings (duration, in the film, review, feeling, passage) are summarised on the scene row. The tree is the overview of the scene's parameters: clicking a group or a node opens the matching inspector tab on that item, where it is managed.
- A resource linked to a scene (by drop or in the manifest) is always an element of its Composition: one that had no element gets one automatically.

- Scene Look tab: an override must be asked for explicitly, with a switch per group (background, palette, fonts), because it departs from the project's base design system. By default the inherited values are shown locked (read-only) with the project's values; turning the switch on unlocks editing for this scene only, turning it off returns to the project value. A drop of a background, palette or look onto a scene asks one short confirmation ("Override for this scene only?") before it creates the override. A scene with an override carries a visible badge in the library, the tree and the reel.

- Known behaviours of W1b to review: a background mood cannot be overridden to "calm" if the project has one (only "revert to project" exists); picking the same value as the project still creates an override.

- The scene inspector is one long form. Split it into tabs: Settings, Effects, Content, Resources (and Look for background and look). Selecting a node of the scene tree opens its tab.
- Seen on screen: a duplicated "Review" heading, a redundant "Ok" status beside the buttons, an "In cuts" field that means nothing to a beginner.
- The app interface is in English while the owner works in French: decide how the interface language is chosen (system language or the project's conversation language).

## Scene content

- Bug seen in use: adding another content item (a second text) makes the existing items lose what was typed, and every text field shows the placeholder "Your words" again.
- "Your words" must be a real placeholder (grey ghost text that disappears as soon as the field has focus), never a stored value. An empty text item stays empty. This may be the cause of the bug above if the default text is saved as content.

- Content is a map of what the scene contains and the instructions for the AI. Items: a text, its colour (linked to the palette, or "AI decides"), its animation (fly in, and so on, or "AI decides"), an optional instruction. The user chooses how much control they want. The order of the items is their processing priority.

## Project and wizard

- Decision (owner, C1, 2026-11-09): the app's instructions to Clap (the start of the Wizard, a build request, a scene draft) never appear as the user's messages; the conversation shows a short neutral line ("Wizard started", "Build requested"). The text is still sent and kept in the transcript; the Sessions view can show it behind "Show the app's instructions", off by default. The durations offered, in the Wizard and in the Manual form, are 30, 45, 60, 75 and 90 seconds, from one constant.

- Packages (PK1): a design can be saved as a package from the project settings, and a new project can start from one (an optional step of New project). The import card (author, dates, version, short hash, integrity, "Not signed", the declared rights and the confirmation box) opens from the library, a double-click or a drop. To judge in the rework: the wording of the sheet and the card, and where the list of packages should live once PK4 adds its window.

- **Built in P5 (2026-11-09).** The choice Wizard or Manual at creation (two cards, Wizard needs a key), Clap leading the interview and proposing the starting pack as cards, the form in sections (formats as tiles, duration with presets and a live feasibility line, film languages as chips, a compact brief with examples as placeholders, three control cards), the base configuration with its "n of 5 set" progress, the interview gate derived from it (no "Mark as validated" button for the interview). The notes below are the owner's remarks that led to it.

- Question (owner): what is the point of switching between Beginner and Expert inside a project? Assessment: little. The wizard only matters while setting a project up; once the base configuration is required (P2) and the workspace is the same for everyone, the toggle changes nothing the user can name. Proposal pending validation: remove the per-project Beginner/Expert switch; one setup form (P5) with a "Guide me step by step" button that opens the wizard for those who want it; the same workspace for everyone, with the Checks tab and Ask Clap as the guidance.
- Owner's refinement (replaces the proposal above): the choice is made when a project is created, not switched afterwards. The app offers two ways in and explains them: Beginner (Clap pre-builds everything from a short brief, then the user lands in the full interface to adjust) and Expert (the user sets the project up by hand in the compact form, then lands in the same interface). Proposal: labels that say who does the work ("Build it with Clap" and "I build it myself", with Beginner and Expert as the subtitle); Beginner needs a key (without one it explains and offers Expert); Clap leads a short interview (the skill's express mode), then presents a starter pack as reviewable cards (base configuration, look, scene list and order, music if supplied), accept all or review each, nothing recorded without the user's acceptance; the same workspace for everyone afterwards.
- Terminology (owner, final): the two ways in are called Wizard and Manual, not Beginner and Expert. Wizard: Clap leads a short interview and pre-builds the starter pack, then the user lands in the full interface. Manual: the user sets the project up by hand in the compact form, then lands in the same interface. The labels in the app are "Wizard" and "Manual", each with a one-line explanation of who does the work. The words Beginner and Expert disappear from the interface (and from the stored setting, renamed accordingly).

- Owner, to revisit later (not a brief yet): the experience of creating a new project must be reviewed again, separately for the Wizard and for Manual, each judged on its own and not as variants of one flow. Seen so far while testing: the Wizard shows the app's own instruction text in the conversation (fixed in lot C1), its duration choices were wrong (30, 45, 60, 75, 90 s decided), and its starting pack has not been judged for quality with a real key. Nothing else is decided: ask the owner what bothers him in each way in before writing a brief.

- Owner, framing for that review: the Wizard and Manual are both wizards, only more or less accompanied (Clap accompanies the first, the app alone the second). So the experience must be simple and fluid in both cases, and use the tool's capabilities and the room of the window to the full (the viewer, the native pickers, the live design board) instead of a form. Proposal pending validation, not decided: one shared skeleton of steps seen in both ways in (Film, Look, Brief, Resources, Scenes, Music), where the Wizard has Clap propose each step for the owner to review and Manual has the owner choose with the app's own pickers; the central viewer showing the project's design system live while a step is edited; the steps list and progress always visible.

- Owner, concrete example for that review: in the Wizard with Clap, the AI has the owner make visual choices (look, palette, fonts, background) as text options in the chat, when it could use the app's predefined looks and pickers. The same holds for the Wizard without Clap (Manual). Direction, to turn into a brief later: a visual choice is always made with the app's visual picker (the looks board, palettes, font specimens, backgrounds, moods), never as text options in the chat; in the Wizard, Clap opens the picker, can preselect or highlight an option with a short reason, and the owner decides by clicking; the same pickers serve the path without Clap. Likely needs a typed way for Clap to present a picker (kind, preselection, reason) and to receive the choice as a proposal.

- The Project form (first screen of a project) is not intuitive or clear: one long column of big empty text areas with small grey help text under each, reel languages typed as a code ("en"), duration as a bare number, no grouping, and a "Mark as validated" button that means nothing to the user. Proposal: sections (Film: formats as aspect-ratio tiles, duration with presets and a live feasibility hint, reel languages as chips from a picker; Brief: audience, message, tone, constraints as compact fields with example placeholders instead of long help text; Control level as three cards with a one-line explanation each); the required base configuration marked as such with a progress indicator ("4 of 5 set"); remove "Mark as validated" (the interview gate is derived from the base configuration being complete, and the Go stays the one explicit validation).

## Resources

- Decision (owner, C1, 2026-11-09): when a Build or an Assemble starts and a Look font has no file, the app asks first (fonts, source, licence, size; Download and continue, Continue with a system font, Cancel). Nothing is downloaded without the yes; the orange Fonts step stays when files are missing.

- **Built in R1 (2026-11-09).** Groups by type (Images, Sounds, Music, Fonts, Other) then by state with folding remembered per project, the preview of the selected resource in the centre (image, sound or music with its tags, cover and a small player, font specimen), tags (stored in `showreel.json`; "placeholder" is the manifest status shown as a tag), a derived "Used in" with clickable scene tags, the four states, Needs attention from automatic checks with the rights question or an accepted risk, and a flagged file hidden from Clap. The AI analysis of resources at adding (R2) is not built. The notes below are the owner's remarks that led to it.

- Group the resources by type, then by status.
- Types: Images, Sounds, Music.
- The central zone is the preview of the selected resource.
- For a music file the centre shows its metadata, the cover image when the metadata holds one, and a simple player (play, pause, scrub).
- Resources can carry tags (for example an image can be a logo or a wallpaper), and the list can be filtered by tag.
- Decided: tags live in `showreel.json` (app mechanics, the skill's manifest format is untouched); Music = `audio` tracks, Sounds = `sfx` and `voice`.
- Resource inspector, seen on screen: "Used in scenes" must not be a free text field. It is derived: show a tag per scene that uses the resource (clickable, selects the scene); linking is done from the scene.
- Simplified resource states (owner's direction, refined): a resource is used or it is not. The user sees four things only: **Available** (in the library, approved because the user added it, not used by any scene yet), **Used in S01, S07** (one clickable tag per scene), **Proposal** (only when the AI analysed something and suggests it: a read-only note giving the AI's reason, and two buttons, Approve or Decline; approving makes the resource approved and links it to the scene), and **Needs attention** (see below). A declined proposal is kept out of sight (collapsed "Declined") so the AI does not propose it again.
- Safety stays, but automatic: the app flags a file by itself (name suggests personal or confidential data, resolution too low, heavy file, rights or consent not confirmed, font licence forbids embedding) and marks it **Needs attention** with the reason in plain words; it cannot be used until the user fixes it (replace the file) or accepts the risk with a short reason (this is the skill's hold and waiver, kept under the hood). No status dropdown for the user to manage.
- Under the hood the skill's manifest statuses stay: Available and Used = approved, Proposal = proposed, Declined = excluded, Needs attention = hold. Placeholder becomes a tag ("placeholder", listed in the release gate).

### Motion: the interface answers (owner, 2026-11-10, after DS1)

The owner likes the motion that DS1 brought and wants more: an interface that responds and lets you understand what is happening. Motion is the visible half of the action/reaction principle, so it must explain cause and effect, not decorate.
- **One motion language, as tokens.** Durations (fast about 120 ms, base about 200 ms, slow about 300 ms) and easing curves (a decelerating curve for things that arrive, an accelerating one for things that leave, a small overshoot only for confirmations) defined once beside the colour tokens, with a speed scale a skin can set (including "off").
- **Patterns by meaning.** Selection moves (a highlight that slides, not jumps); a change of state shows itself (a status icon changes with a short morph or pulse, a switch slides); arrival and departure keep their place (a new scene opens a gap, a deleted one closes it, Undo plays it back); a refusal nudges the control and shows the reason where the eye is; progress is shown where the work is (the scene rows of a Build show waiting, writing, testing and repairing differently, a finished scene settles); a panel that opens or collapses moves from where it will live.
