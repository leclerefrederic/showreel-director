# Steps 2 and 2b detail: style sheet, storyboard, scene-by-scene review

## Step 2 — Style sheet and storyboard

Starting from the approved `brief.md`, write a seven-line style sheet to `style-sheet.md` (intended feeling and emotional arc, palette, type, motion vocabulary, energy curve, key moment, music approach), show a swatch or still if you can render one, and validate it with a decision sheet (one item per line that has real alternatives, the proposed value as the recommended option plus two alternatives, palette with swatches, type with a specimen of the message), never a text block with "OK?". Also write a storyboard as a file (`storyboard.md`, never only a chat summary; time, scene, on-screen text, image and motion, feeling and tension level, any gag or beat, handoff to the next scene), with a stable ID per scene (S01, S02…; an ID is never reused or renumbered: a new scene gets the next number or a suffix such as S04b, a ditched ID stays marked as ditched) and, when cut-downs exist, an "in cuts" column; refresh it after big feedback rounds. Before showing it, run the checks in `references/storyboard-review.md` and fix what fails. `references/script-examples.md` shows the writing principle in three deliberately different tones; write in the user's voice, not theirs. When the user supplies a storyboard, treat its time ranges as the scene windows of the existing code, and list what you could not implement instead of silently dropping it.

## Step 2b — Scene-by-scene review (gate before generation)

Once the storyboard is drafted and has passed its checks, go through it with the user (first build the visual sheet of scene cards with `scripts/build_scene_cards.py`, passing the brand colours and font, and present the HTML file so the user sees the whole film at once with OK / MODIFY / DITCH buttons; skip the sheet only if the session cannot write or present files, and say so; see `references/scene-review.md`). If the user marked scenes on the sheet, scenes marked OK are locked and only MODIFY, DITCH and undecided scenes are discussed, one at a time; otherwise follow `references/scene-review.md`: show a short card for each scene (role, timing, text, image and motion, effects, feeling and tension, assets, numbers), ask OK / MODIFY / DITCH (plus "OK for this and all the remaining"), and repeat on the same scene until the user decides before moving to the next. Lock approved scenes, recompute the timeline and the feasibility check after every change, and show what a DITCH leaves open before confirming it. When every scene is decided, run the global pass (storyboard checks, translations, release gate), rewrite `storyboard.md` as the next version with a change log, update the brief, and ask for an explicit go. **Do not start the build before that go.** The final storyboard is presented as a file (and on the card sheet), the user validates it, and only then you ask for the go in a message of its own; no summary of the storyboard is pasted in the chat.
