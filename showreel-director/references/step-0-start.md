# Step 0 detail: interaction, environment, round 0, folder

The rules summarised in SKILL.md, in full. Gates table, untrusted-content rule and folder layout stay in SKILL.md.

**Interaction rule (applies to every step).** The user is never asked to read a block of text and approve it. Every decision goes through the question tool (1 to 4 decisions per round, 2 to 4 options, recommended first, one short sentence of context) or through a page the user operates: a **decision sheet** when there are 5 or more decisions or when the user must see something (colours, type, structure options, brief sections, release gate), the effects lab, the scene cards, the look test, the notes pad of a review build (`references/review-tools.md`). Long content (brief, style sheet, storyboard) lives in a file in the project folder; present the file, then validate it with one of those tools, never with "OK?" under a wall of text. Anything you derive (a structure, a timeline, a table) goes into the brief or a sheet, not into the chat. Text replies carry a few lines at most: what you did, what you ask next. Nothing is pre-accepted: an option the user did not pick is never recorded as a decision (a recommended default is recorded as an *assumption*, only when the user delegated). In a plain-text environment, number the options and ask one round at a time (`references/portability.md`).

**Pages in the user's language.** Every page the user operates (decision sheets, scene cards, the lab, the notes pad) speaks the conversation language: pass `--ui` with the translated texts (keys listed in each script's header; the pad uses the `ui` block of `main.js`) and `--lang`. Copied results then come back in that language; keep the canonical words OK / MODIFY / DITCH.

**Environment check, first thing when invoked, before anything else.** Take stock of the session's tools (questions, folder request, show files, shell, screenshot, web) and, with a shell, run `python3 scripts/check_env.py --notice` (details in `references/engine.md`; save `--json` in `qa/` once the folder exists). If anything is missing, the first reply opens with a short degraded-mode notice: what is lost, how to get the full mode, and that you can continue as is (fallbacks in `references/portability.md`). Never install without asking or hide a missing tool; repeat the notice in the final report if it still applies.

**First reply language.** Until round 0 is answered, write in the language of the user's message; round 0 closes that first reply (any asset problems or vague words you must name come before it, briefly).

**Round 0, always the very first question.** (a) The language we talk in during the project (questions, brief, storyboard notes, reports); it is independent of the reel. Recommend the language the user wrote in, and use the chosen language for everything addressed to the user. (b) The language(s) shown on screen in the reel: **default English**, then optional additional languages, which one is the master text, adapted or literal translation. Ask both in the same round so the difference is visible.

**Working folder, right after round 0.** The project produces many files, so it needs a folder that persists and that the user can open. If none is connected, request one with the session's directory-request tool if it has one (load it first if its schema is deferred), phrased in the conversation language, and wait; otherwise ask for a folder path. Check it for existing material (assets, an earlier `brief.md`, version folders) and reuse it instead of asking again. If the user declines, work in the temporary outputs folder and say clearly that those files are scratch and may disappear. Refer to the folder by its name, never by an internal path. Record the environment result in the brief (manual fallbacks included).

**Waiving gates and existing projects.** Also in `references/process-rules.md`: external actions need an explicit yes, sensitive non-image files are held, look-test text changes need a fresh go, storyboards are archived before rewriting. Two special routes, detailed there: (1) if the user explicitly asks to skip a gate, confirm once with a two-option question (keep the gate, recommended and first; or skip and record), record every skipped decision as an assumption, mark the build as a draft, keep the release gate and close the waiver when the first full build is validated; (2) if the folder holds earlier work or the user wants to change an existing reel, ask whether to continue the latest version, start a new version from the brief, or start a new project, and apply the new-version rules (a new track always triggers the rights check, the audio analysis, re-snapping to bars and a new feasibility run).
